# n8n workflows and database (Phases 6–7)

n8n owns the business logic. The voice engine only calls these webhooks (signed) during a call.
PostgreSQL (schema `va`) stores everything. Generated by `tools/build_workflows.py`, imported and
published automatically by notebook cell 10 (`ops/n8n.py: install_workflows`).

## Workflows

| Workflow | Trigger | Covers (original requirement list) |
|---|---|---|
| **VA Session Start** | `POST /webhook/voice/session-start` | Call Router, Business Configuration, Customer Lookup, Customer Memory |
| **VA Tool** | `POST /webhook/voice/tool` | AI Tool Execution, Order Management, Booking & Reservations, Human Handoff |
| **VA Session End** | `POST /webhook/voice/session-end` | Post-Call Processing (transcript, usage, LLM summary, memory) |
| **VA Call Event** | `POST /webhook/voice/call-event` | Call status tracking for the phone line |
| **VA Outbound Scheduler** | every minute | Outbound Call Scheduler (consent, opt-out, calling hours, retries) |
| **VA Notifications** | every minute | Notifications (delivers queued events to a webhook you configure) |
| **VA Error Handler** | any workflow error | Error Handling and Monitoring (`va.workflow_errors`) |

"Voice Session Orchestration" and "Incoming Call Handler" are covered by Session Start / End together
with the voice engine. Business rules live in n8n **Code** nodes. SQL only reads and writes data, and every
query is scoped by `business_id`.

## Security on every webhook
1. **HMAC node** (n8n Crypto node, secret in the encrypted credential *VA webhook HMAC*) computes
   `HMAC-SHA256(secret, "<X-VA-Timestamp>.<payload>")`.
2. **Verify request** compares it with `X-VA-Signature` (constant time), rejects timestamps older than
   5 minutes, and parses `payload`. Anything else gets **401**.
3. The voice engine sends `{"payload": "<JSON string>"}`, so the exact signed bytes reach n8n
   (n8n re-serialises parsed JSON, which would break a signature over the raw body).
4. Tool calls carry `X-VA-Idempotency-Key`. Responses are stored in `va.idempotency_keys`, and a retried
   call returns the stored response instead of creating a second order.
5. **Business authorisation:** a tool call only runs if its `session_id` is a call of that `business_id`.

## Webhook contracts (inside `payload`)

**session-start**: request `{session_id, channel: browser_test|gsm|sip, line, direction, caller: {number}, call_id, context: {business_id?}}`.
Response `{ok, session_id, business_id, business_name, agent_instructions, language, knowledge[], customer{}, tools[], greeting{en,ur}, max_call_seconds, recording_consent_required}`.
The business is chosen from `context.business_id` (outbound calls), else from the `(channel, line)` row in
`va.business_phone_numbers` (browser test → line `default`). A caller number creates or finds the customer.

**tool**: request `{session_id, business_id, call_id, tool, arguments}`. Response `{ok: true, result}` or `{ok: false, error}`.

| tool | arguments | rules (n8n Code nodes) |
|---|---|---|
| get_menu | `category?` | only available items of this business |
| lookup_order | `order_number` | digits 4–10 |
| create_order | `items[{sku, quantity}]`, `delivery_address`, `customer_name?`, `customer_phone?` | SKUs must exist and be available; qty 1–20; address required; caller must be identified (from caller ID or `customer_phone`); total computed in n8n |
| confirm_order | `order_number`, `decision: confirm\|cancel` | only `pending` orders can change |
| check_availability | `date YYYY-MM-DD`, `time HH:MM`, `party_size` | opening hours, not in the past, seats per time slot |
| create_booking | same + `name`, `customer_phone?` | same checks, then reference `BK-####` |
| remember_customer_preference | `note` | needs an identified caller |
| request_human_handoff | `reason` | creates `va.handoff_requests` + a notification (no live transfer) |

**session-end**: request `{session_id, business_id, started_at, ended_at, end_reason, turns, transcript[{role, text, language, interrupted, t}]}`.
It closes the call, stores the transcript and usage, responds, and *then* asks the local LLM for a summary,
an outcome and anything to remember (saved to `va.conversation_summaries` / `va.customer_memory`).

**call-event**: request `{call_id, status, reason, direction, remote_number, context{business_id, job_id}}`.
It records the event once per status and updates the matching outbound job (completed, or retried up to `max_attempts`).

## Using it
**Notifications** (e.g. a Discord/Slack/Telegram-bot incoming webhook URL):
```sql
INSERT INTO va.business_integrations (business_id, kind, config)
SELECT id, 'notify_webhook', '{"url": "https://discord.com/api/webhooks/..."}' FROM va.businesses WHERE slug = 'karachi-pizza';
```
Without one, notifications stay queued in `va.notifications`.

**Outbound call** (needs the phone gateway, Phase 5; until then jobs fail with `gateway_not_connected` and retry):
```sql
UPDATE va.customers SET consent_outbound = true, consent_recorded_at = now() WHERE phone_e164 = '+923001234567';
INSERT INTO va.outbound_jobs (business_id, customer_id, purpose, context)
SELECT c.business_id, c.id, 'order_confirmation', '{"order_number": "4821"}' FROM va.customers c WHERE c.phone_e164 = '+923001234567';
```
